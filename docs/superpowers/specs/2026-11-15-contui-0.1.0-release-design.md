# contUI 0.1.0 release — design

Date: 2026-11-15
Status: awaiting approval
Supersedes: the "No bottles" and "No automation" non-goals of
`2026-11-14-homebrew-tap-design.md`

## Intent

`brew install adgan/tap/contui` must install a prebuilt app in seconds, with no Rust
toolchain and no compile. Today it is `--HEAD` only and builds from source for ~90
seconds. That is fine for the author and wrong for anyone else.

The first tag, `v0.1.0`, is the point where the tap stops being a source build. It also
exercises the release path end to end so 0.1.1 is a repeat, not a re-discovery.

Scope for now is deliberately narrow: **up-to-date macOS only** — arm64, macOS 26
(Tahoe). Homebrew 5 moved Intel to Tier 3 and stopped bottling it, and older macOS is not
being tested, so neither gets an artifact yet.

## Goals

1. Tagging `v0.1.0` publishes a GitHub release with the source tarball and an
   `arm64_tahoe` bottle, plus the exact formula text the tap needs.
2. `brew install adgan/tap/contui` on arm64 macOS 26 pours the bottle: no `rust`
   formula installed, no `cargo` invoked, `brew list --versions` reports `0.1.0`.
3. The release path is repeatable: the next tag needs a version bump and a push, nothing
   else, and the workflow prints everything the tap update needs.
4. `brew install --HEAD` keeps working unchanged for development.

## Non-goals

- Intel (`tahoe`) and older-macOS(`sequoia`) bottles.
- Notarization, Developer ID signing, or a cask. The app stays ad-hoc signed; the first
  launch may still need right-click → Open.
- ghcr.io hosting. Uploading to Homebrew's OCI registry needs a registry token and
  `brew pr-upload`; a public release asset needs neither.
- Auto-bumping `version` from `Cargo.toml`, changelog generation, `brew audit` rework.
- Any change to app behaviour. This is packaging only.

## Anti-goals

- A bottle whose formula still declares `depends_on "rust" => :build` in a way that makes
  brew install Rust even when pouring. Pulling a bottle must never touch a compiler.
- A formula that silently source-builds on Sequoia or Intel and looks like it worked. If
  the platform is unsupported, `brew install` must say so up front.
- A `url` pointing at GitHub's auto-generated `archive/refs/tags/v0.1.0.tar.gz`. GitHub
  regenerates those tarballs and their sha256 can change, which turns every install into a
  checksum failure.
- A release that exists on paper only: tag pushed, no artifacts, formula unchanged.

## Constraints

- Tag: `v0.1.0` on current `main` (commit `dfd76e6`). `Cargo.toml`, `assets/Info.plist`
  and the tap formula already say `0.1.0`; `CFBundleVersion` stays `1`.
- Bottle label is `arm64_tahoe`, produced by a `macos-26` GitHub-hosted runner (arm64,
  macOS 26.7.x — the same OS as this machine).
- Bottles are built by `brew install --build-bottle` + `brew bottle`; the bottle DSL is
  whatever `brew bottle --json` emits (its `cellar:` value is taken from that output, not
  guessed).
- Tap: `github.com/adgan/homebrew-tap`, file `Formula/contui.rb`.
- `gh` is authenticated as `adgan` with `repo` scope; the tap is public, so no extra
  secret is required for this design.
- The app bundle must still be ad-hoc codesigned inside the formula's `install`; a bottle
  ships the already-signed bundle.

## Approaches considered

**1. Bottle built in Actions on the tag, hosted as a release asset (chosen).** The
workflow builds the bottle on `macos-26`, uploads it next to the source tarball, and
prints the `bottle do` block. `root_url` points at the release. Costs: a workflow that
must stay green, and a machine-built artifact we cannot re-verify locally except by
installing it. Buys: repeatable, no local toolchain, no registry credentials, and the
build happens in a clean environment rather than on the author's machine.

**2. Bottle built locally and uploaded by hand.** Fastest first release (this Mac is
already arm64 Tahoe). Rejected as the design: it makes 0.1.1 manual again, ties the
artifact to whatever is in the local Cellar, and leaves no record of how it was built.

**3. A cask instead of a formula.** The conventional shape for a GUI `.app`, and it
installs into `/Applications`. Rejected for now: an ad-hoc-signed, un-notarized cask gets
blocked by Gatekeeper on install, and Homebrew deprecated unsigned casks in 2026. The
formula persists; a cask can come with a Developer ID later.

## Architecture

```
adgan/contui (source repo)
  .github/workflows/release.yml   tag -> release + source tarball + arm64_tahoe bottle
adgan/homebrew-tap (tap)
  Formula/contui.rb               stable url + sha256 + bottle block; head kept
```

`release.yml`, on `push: tags: v*` (single job, `macos-26`):

1. Checkout the tag; read the version from `Cargo.toml`; fail if the tag is not
   `v<version>`.
2. `git archive --format=tar.gz --prefix=contui-<version>/` → `contui-<version>.tar.gz`,
   record its sha256, `gh release create` (or attach to an existing release) and upload.
3. Write a formula copy into a temporary tap directory with `url` = the release asset and
   that sha256 (same `install`/`caveats`/`test` as the tap), `brew install --build-bottle`
   it, `brew bottle --json --no-rebuild` it.
4. Upload the bottle tarball to the same release.
5. Emit to the job summary: the bottle's sha256, the complete `bottle do` block, and the
   full new `Formula/contui.rb`, ready to paste into the tap.

`Formula/contui.rb` changes:

- `url "https://github.com/adgan/contui/releases/download/v0.1.0/contui-0.1.0.tar.gz"`
  with `sha256`, plus `bottle do root_url "…/download/v0.1.0" … end`.
- `depends_on macos: :tahoe` and `depends_on arch: :arm64`, so an unsupported machine
  fails with a clear message instead of compiling for 90 seconds.
- `depends_on "rust" => :build` stays: it only applies when brew actually builds.
- `head` stays as-is.

Verification, on this machine: `brew uninstall contui`, `brew install
adgan/tap/contui`, then check that brew downloaded a bottle (no `rust` dependency
installed), `brew list --versions contui` says `0.1.0`, the binary and bundle exist, and
the app launches. A second `brew uninstall && brew install` after touching nothing must
hit the download cache and be fast. `brew test adgan/tap/contui` and
`brew audit --strict --online` must pass.

## Decisions made here, for review

- **Manual tap update, no PAT.** The workflow prints the formula; the maintainer pastes
  and pushes. A cross-repo push needs a `TAP_TOKEN` secret and write access to a second
  repo; the value is one paste per release. Automating it is a later, separate change.
- **`depends_on macos: :tahoe`** rather than the default "source-build anywhere". It
  matches the stated scope and keeps the formula honest. Removing it later is one line.
- **Release notes**: short, from the README's feature list, not generated from commits.
- **`--no-rebuild`** on `brew bottle`, so the filename carries no rebuild suffix.

## Update 2026-11-15 — two jobs, to keep macOS minutes minimal

The single `macos-26` job is split. `ubuntu-24.04-arm` builds the source tarball, creates
the release and writes the stable formula; `macos-26` runs only `brew install
--build-bottle`, `brew bottle`, and the uploads, from a `scripts`-only checkout. The
release is still dispatched by hand (`workflow_dispatch`, input `version`) — no tag push
starts a run. Rationale: macOS runners are the expensive leg, and nothing about the
tarball or the formula needs macOS.

## What's left to the builder

- The exact `brew bottle --json` invocation and how to parse the emitted DSL without
  hand-writing the sha; whether `--build-bottle` needs `HOMEBREW_NO_INSTALL_FROM_API`.
- Whether `git archive` output or `tar czf` is used for the source tarball, and the
  `--prefix` shape the formula's `cargo install` tolerates.
- Whether the workflow needs `dtolnay/rust-toolchain` or relies on Homebrew's `rust`
  dependency; Homebrew's is preferred so the bottle matches the formula.
- Release body wording, and whether the tap README's release checklist is updated in the
  same pass.
